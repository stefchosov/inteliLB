================================================================================
  inteliLB — RUNBOOK
  Intelligent Load Balancer Research Project
================================================================================

This runbook covers everything from first-time setup through running all
experiments and collecting results for analysis.

The experiment compares 6 load balancing algorithms across 3 Azure backends
with intentionally asymmetric CPU capacity (1 / 2 / 4 vCPUs) to measure how
well each algorithm adapts to real-world resource constraints.

PART 2 — LOCAL SMOKE TEST
================================================================================

Use this to verify the code works before spending money on Azure. Run each
component directly with go run — no containers needed.

NOTE: In local mode all backends run on your full machine with no CPU limits,
so you won't see the 1/2/4 core asymmetry. This is just a code/wiring check.
The real experiment happens against the Azure VMs in Part 3.

--- Start the backends (3 separate terminals) --------------------------------

  Terminal 1:
    REGION=us-east ID=backend-1 go run ./cmd/backend -port=8081

  Terminal 2:
    REGION=us-west ID=backend-2 go run ./cmd/backend -port=8082

  Terminal 3:
    REGION=eu-west ID=backend-3 go run ./cmd/backend -port=8083

  Wait for each to print:
    backend backend-N (<region>) listening on :808N

--- Start the load balancer (4th terminal) -----------------------------------

  go run ./cmd/loadbalancer \
    -port=8080 \
    -algorithm=intelligent \
    -backends="http://localhost:8081,http://localhost:8082,http://localhost:8083"

--- Smoke tests (5th terminal) -----------------------------------------------

  # Route a request through the LB
  curl "http://localhost:8080/work?intensity=3"

  Expected:
    {"result":"<hash>","duration_ms":<n>,"region":"...","id":"backend-N"}

  # Check stats — all 3 backends should be healthy
  curl http://localhost:8080/lb/stats | python3 -m json.tool

  # Verify individual backends respond
  curl http://localhost:8081/health
  curl http://localhost:8082/health
  curl http://localhost:8083/health

  # Confirm algorithm hot-swap works
  curl -s -X POST http://localhost:8080/lb/algorithm \
    -H "Content-Type: application/json" \
    -d '{"algorithm":"round_robin"}'

  # Run a short client test
  mkdir -p results
  go run ./cmd/client \
    -url=http://localhost:8080 \
    -workers=5 \
    -duration=20s \
    -intensity=3 \
    -output=results/smoke.csv

  Expected: results/smoke.csv has rows with error=false

--- Stop local services ------------------------------------------------------

  Ctrl+C in each terminal (backends and LB)

PART 3 — AZURE DEPLOYMENT
================================================================================

--- One-time: Azure login ----------------------------------------------------

  az login
  # A browser window opens — sign in with your student account.

  # Verify your subscription:
  az account show --output table

--- One-time: SSH key (if you don't already have one) -----------------------

  ssh-keygen -t rsa -b 4096 -f ~/.ssh/id_rsa
  # Press Enter for no passphrase (or set one if you prefer)

--- Deploy backends to Azure -------------------------------------------------

  ./scripts/deploy.sh

  This will:
    1. Create 3 resource groups (one per region)
    2. Create VMs:
         eastus       backend-1  Standard_B1ms  — 1 vCPU   ~$0.021/hr
         westus2      backend-2  Standard_B2s   — 2 vCPUs  ~$0.042/hr
         westeurope   backend-3  Standard_B4ms  — 4 vCPUs  ~$0.166/hr
    3. Open port 8080 on each VM
    4. Cross-compile the backend binary and copy it to each VM via SCP
    5. Start the backend process on each VM
    6. Print the go run command with your backend IPs

  Expected total time: 8–12 minutes.

  SAVE THE OUTPUT — it contains your backend URLs.

--- Verify backends are reachable --------------------------------------------

  # Replace IPs with the ones printed by deploy.sh
  curl http://<eastus-ip>:8080/health
  curl http://<westus2-ip>:8080/health
  curl http://<westeurope-ip>:8080/health

  Each should return: {"status":"ok","region":"...","id":"backend-N"}

  # Check CPU counts reflect actual VM vCPUs
  curl http://<eastus-ip>:8080/metrics      # expect "num_cpus": 1
  curl http://<westus2-ip>:8080/metrics     # expect "num_cpus": 2
  curl http://<westeurope-ip>:8080/metrics  # expect "num_cpus": 4

PART 4 — RUNNING THE LOAD BALANCER LOCALLY
================================================================================

The LB runs on your machine and proxies to the Azure backends.

--- Start the load balancer --------------------------------------------------

  Use the command printed at the end of deploy.sh. Example:

    go run ./cmd/loadbalancer \
      -port=8080 \
      -algorithm=intelligent \
      -backends="http://<eastus-ip>:8080,http://<westus2-ip>:8080,http://<westeurope-ip>:8080"

  Leave this running in its own terminal for the entire experiment session.

--- Verify end-to-end routing ------------------------------------------------

  curl "http://localhost:8080/work?intensity=3"
  curl http://localhost:8080/lb/stats | python3 -m json.tool

  The stats should show all 3 backends as healthy with real latency values
  reflecting actual cross-region round-trip times.

  Typical cross-region RTTs from US:
    Your machine → eastus:     10–60ms
    Your machine → westus2:    20–80ms
    Your machine → westeurope: 80–200ms

PART 5 — EXPERIMENT PROTOCOL
================================================================================

The goal is to compare all 6 algorithms under identical load.

--- Algorithms to test -------------------------------------------------------

  1. round_robin
  2. lowest_latency
  3. least_connections
  4. lowest_cpu
  5. intelligent
  6. adaptive

--- Recommended parameters ---------------------------------------------------

  Workers  : 20       (20 concurrent clients — enough to saturate backend-1)
  Duration : 120s     (2 minutes — gives adaptive time to adjust weights)
  Intensity: 7        (high CPU load, stresses the asymmetric backends)

  Rationale: at intensity=7 with 20 workers, backend-1 (1 vCPU) will approach
  100% CPU while backend-3 (4 vCPUs) stays well below 50%. This is the
  condition where intelligent/adaptive routing provides the most benefit.

--- Running the experiments --------------------------------------------------

  mkdir -p results

  Run each algorithm in sequence. Wait ~30s between runs for backends to
  cool down (CPU % to drop back to idle).

  ALGORITHM 1: round_robin
  ------------------------

    curl -s -X POST http://localhost:8080/lb/algorithm \
      -H "Content-Type: application/json" \
      -d '{"algorithm":"round_robin"}'

    go run ./cmd/client \
      -url=http://localhost:8080 \
      -workers=20 \
      -duration=120s \
      -intensity=7 \
      -output=results/round_robin.csv

    curl -s http://localhost:8080/lb/stats > results/round_robin_stats.json
    sleep 30

  ALGORITHM 2: lowest_latency
  ---------------------------

    curl -s -X POST http://localhost:8080/lb/algorithm \
      -H "Content-Type: application/json" \
      -d '{"algorithm":"lowest_latency"}'

    go run ./cmd/client \
      -url=http://localhost:8080 \
      -workers=20 \
      -duration=120s \
      -intensity=7 \
      -output=results/lowest_latency.csv

    curl -s http://localhost:8080/lb/stats > results/lowest_latency_stats.json
    sleep 30

  ALGORITHM 3: least_connections
  -------------------------------

    curl -s -X POST http://localhost:8080/lb/algorithm \
      -H "Content-Type: application/json" \
      -d '{"algorithm":"least_connections"}'

    go run ./cmd/client \
      -url=http://localhost:8080 \
      -workers=20 \
      -duration=120s \
      -intensity=7 \
      -output=results/least_connections.csv

    curl -s http://localhost:8080/lb/stats > results/least_connections_stats.json
    sleep 30

  ALGORITHM 4: lowest_cpu
  ------------------------

    curl -s -X POST http://localhost:8080/lb/algorithm \
      -H "Content-Type: application/json" \
      -d '{"algorithm":"lowest_cpu"}'

    go run ./cmd/client \
      -url=http://localhost:8080 \
      -workers=20 \
      -duration=120s \
      -intensity=7 \
      -output=results/lowest_cpu.csv

    curl -s http://localhost:8080/lb/stats > results/lowest_cpu_stats.json
    sleep 30

  ALGORITHM 5: intelligent
  -------------------------

    curl -s -X POST http://localhost:8080/lb/algorithm \
      -H "Content-Type: application/json" \
      -d '{"algorithm":"intelligent"}'

    go run ./cmd/client \
      -url=http://localhost:8080 \
      -workers=20 \
      -duration=120s \
      -intensity=7 \
      -output=results/intelligent.csv

    curl -s http://localhost:8080/lb/stats > results/intelligent_stats.json

  ALGORITHM 6: adaptive
  ----------------------

    curl -s -X POST http://localhost:8080/lb/algorithm \
      -H "Content-Type: application/json" \
      -d '{"algorithm":"adaptive"}'

    # NOTE: adaptive adjusts its weights every 30s — run for 120s to capture
    # at least 3 adjustment cycles.
    go run ./cmd/client \
      -url=http://localhost:8080 \
      -workers=20 \
      -duration=120s \
      -intensity=7 \
      -output=results/adaptive.csv

    curl -s http://localhost:8080/lb/stats > results/adaptive_stats.json

PART 6 — COLLECTING RESULTS
================================================================================

After all runs you will have:

  results/
  ├── round_robin.csv           round_robin_stats.json
  ├── lowest_latency.csv        lowest_latency_stats.json
  ├── least_connections.csv     least_connections_stats.json
  ├── lowest_cpu.csv            lowest_cpu_stats.json
  ├── intelligent.csv           intelligent_stats.json
  └── adaptive.csv              adaptive_stats.json

--- CSV format (per row) -----------------------------------------------------

  timestamp_ms,duration_ms,error
  1709000000000,142.00,false

  - timestamp_ms  : Unix epoch milliseconds when the request started
  - duration_ms   : End-to-end latency (network + compute)
  - error         : true if HTTP 5xx or connection failure

--- Stats JSON format --------------------------------------------------------

  {
    "algorithm": "intelligent",
    "total_requests": 1840,
    "backends": [
      {
        "id": "backend-1", "region": "eastus",
        "healthy": true,
        "cpu_percent": 94.2,
        "avg_latency_ms": 287.4,
        "total_requests": 210,
        "failed_requests": 3
      },
      ...
    ]
  }

--- Key metrics for your analysis table --------------------------------------

  From each *_stats.json:
    - total_requests
    - per-backend request distribution (% of total)
    - per-backend avg_latency_ms
    - per-backend cpu_percent at end of run

  From each *.csv:
    - p50 / p95 / p99 latency
    - error rate (% of rows where error=true)
    - throughput (total rows / 120 seconds)

  Quick Python snippet to compute percentiles:

    python3 - <<'EOF'
    import csv, sys
    rows = list(csv.DictReader(open(sys.argv[1])))
    lats = sorted(float(r['duration_ms']) for r in rows if r['error']=='false')
    n = len(lats)
    errs = sum(1 for r in rows if r['error']=='true')
    print(f"n={len(rows)}  errors={errs}  "
          f"p50={lats[int(n*.50)]:.1f}  "
          f"p95={lats[int(n*.95)]:.1f}  "
          f"p99={lats[int(n*.99)]:.1f} ms")
    EOF
    # Usage: python3 - results/intelligent.csv

--- Suggested analysis angles ------------------------------------------------

  1. LATENCY COMPARISON
     Bar chart: p50 / p95 / p99 for all 6 algorithms side by side.
     Expected: intelligent and adaptive outperform round_robin at p99.

  2. REQUEST DISTRIBUTION
     Stacked bar: % of requests to each backend per algorithm.
     Expected: round_robin is 33/33/33. intelligent/adaptive send far
     fewer requests to backend-1 (1 vCPU).

  3. CPU UTILIZATION PER BACKEND
     Grouped bar: cpu_percent per backend per algorithm.
     Expected: round_robin drives backend-1 into saturation (>90%).
     intelligent/adaptive keep utilization more even.

  4. ERROR RATE
     Table or bar chart. round_robin will have the highest error rate
     because backend-1 gets overwhelmed and starts failing.

  5. ADAPTIVE WEIGHT EVOLUTION (qualitative)
     Describe how adaptive detects high CPU variance and shifts weight
     toward the CPU metric, effectively becoming lowest_cpu dynamically.

APPENDIX — TROUBLESHOOTING
================================================================================

PROBLEM: "no healthy backends" from the LB
  -> Backend may still be starting. Wait 30s and retry.
  -> Check backend is reachable: curl http://<ip>:8080/health
  -> SSH in and check the process:
       ssh -i ~/.ssh/id_rsa azureuser@<ip>
       pgrep -a inteliLB-backend
       cat /var/log/inteliLB-backend.log

PROBLEM: SSH connection refused during deploy
  -> Wait another 30–60s for the VM to finish booting, then re-run manually:
       PUBLIC_IP=<ip> SSH_USER=azureuser KEY_FILE=~/.ssh/id_rsa \
         REGION=eastus ID=backend-1 \
         ./scripts/deploy-backend.sh

PROBLEM: "permission denied" when SCP copies the binary
  -> Check your SSH key: ssh -i ~/.ssh/id_rsa azureuser@<ip> echo ok
  -> Ensure KEY_FILE points to the private key (not the .pub file)

PROBLEM: go mod tidy fails
  -> Ensure Go 1.21+ is installed and $GOPATH/bin is in your PATH.
  -> Try: GOFLAGS="-mod=mod" go mod tidy

PROBLEM: backend-1 (1 vCPU) shows num_cpus > 1
  -> Standard_B1ms has 1 vCPU — if num_cpus reports higher, the binary
     may have been deployed to the wrong VM. Re-check the IP assignments
     from the deploy output.

PROBLEM: adaptive algorithm not changing weights
  -> Adaptive recalculates every 30s. Run the test for at least 90s.
  -> Weights only shift when there is measurable variance between backends.
     Ensure intensity is 7+ to create real CPU differences.

PROBLEM: results CSV is empty
  -> Check the LB is running and reachable: curl http://localhost:8080/lb/stats
  -> Try a manual request first: curl "http://localhost:8080/work?intensity=2"
