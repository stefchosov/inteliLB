inteliLB demo — ~10 min end-to-end
================================================================================

Backends need to already be up on Azure. If they're not, run ./scripts/deploy.sh
first — that takes about 10 min and I only need to do it once.

Settings I'm using:
  20 workers, 30s runs, intensity 7, 20s cooldown between algos
  (20 workers at intensity 7 saturates backend-1's single vCPU while
   backend-2 and backend-3 still have room — that gap is what makes
   the smart algorithms look better than round robin)

Rough timing:
  setup ~1 min + 6x 30s runs + 5x 20s cooldowns + teardown ~1 min = ~7 min total

================================================================================
1. START UP
================================================================================

Open two terminals in the project root.
  Terminal A — LB process, stays open the whole time
  Terminal B — where I run client commands

Terminal A — paste in the backend IPs from the deploy output:

  go run ./cmd/loadbalancer \
    -port=8080 \
    -algorithm=round_robin \
    -backends="http://<eastus-ip>:8080,http://<westus2-ip>:8080,http://<eastus2-ip2>:8080"

Wait for: load balancer listening on :8080

Terminal B — make sure all 3 backends are healthy before starting:

  curl http://localhost:8080/lb/stats | python3 -m json.tool

All three should show "healthy": true. If any don't, stop and debug before demoing.

  mkdir -p results/demo

IMPORTANT: Restart the LB process (Ctrl+C in Terminal A, then re-run) between each
algorithm switch. The /lb/stats counters are cumulative for the lifetime of the process
— if you don't restart, the backend distribution shown by demo_summary.py will include
all previous runs and look like a split even for algorithms that route to a single backend.

================================================================================
2. RUN THE ALGORITHMS
================================================================================

────────────────────────────────
round_robin  (1/6)
────────────────────────────────

  curl -s -X POST http://localhost:8080/lb/algorithm \
    -H "Content-Type: application/json" \
    -d '{"algorithm":"round_robin"}' | python3 -m json.tool

  go run ./cmd/client \
    -url=http://localhost:8080 \
    -workers=20 \
    -duration=30s \
    -intensity=7 \
    -output=results/demo/round_robin.csv

  curl -s http://localhost:8080/lb/stats > results/demo/round_robin_stats.json
  echo "cooling..."; sleep 20

  Point out: ~33% to each backend. Backend-1 is hammered — high CPU, high latency.
  This is the baseline that everything else should beat.

────────────────────────────────
lowest_latency  (2/6)
────────────────────────────────

  Restart LB in Terminal A with -algorithm=lowest_latency (or Ctrl+C and re-run).

  go run ./cmd/client \
    -url=http://localhost:8080 \
    -workers=20 \
    -duration=30s \
    -intensity=7 \
    -output=results/demo/lowest_latency.csv

  curl -s http://localhost:8080/lb/stats > results/demo/lowest_latency_stats.json
  echo "cooling..."; sleep 20

  Point out: routes 100% to backend-2 (northcentralus, ~14ms RTT) — pure network
  proximity. Optimal for I/O-bound work but concentrates all CPU-heavy traffic on
  a 2-vCPU backend while backend-3's 4 vCPUs sit completely idle. Saturates at
  75 req/s in the full sweep.

────────────────────────────────
least_connections  (3/6)
────────────────────────────────

  Restart LB in Terminal A with -algorithm=least_connections.

  go run ./cmd/client \
    -url=http://localhost:8080 \
    -workers=20 \
    -duration=30s \
    -intensity=7 \
    -output=results/demo/least_connections.csv

  curl -s http://localhost:8080/lb/stats > results/demo/least_connections_stats.json
  echo "cooling..."; sleep 20

  Point out: tracks in-flight requests per backend — no polling needed. Backend-3
  (4 vCPU) drains connections faster so it attracts more traffic implicitly.
  Best p99 of any algorithm on CPU-bound workloads. RTT tiebreaker prevents
  tie-breaking bias toward backend-1.

────────────────────────────────
lowest_cpu  (4/6)
────────────────────────────────

  Restart LB in Terminal A with -algorithm=lowest_cpu.

  go run ./cmd/client \
    -url=http://localhost:8080 \
    -workers=20 \
    -duration=30s \
    -intensity=7 \
    -output=results/demo/lowest_cpu.csv

  curl -s http://localhost:8080/lb/stats > results/demo/lowest_cpu_stats.json
  echo "cooling..."; sleep 20

  Point out: correctly avoids backend-1 (~18% share) since it sits at 100% CPU.
  However CPU% doesn't distinguish capacity — a 4-vCPU backend doing 4x the work
  reports similar CPU% to a 1-vCPU backend doing 1x the work, so routing between
  b2 and b3 is noisy.

────────────────────────────────
intelligent  (5/6)
────────────────────────────────

  Restart LB in Terminal A with -algorithm=intelligent.

  go run ./cmd/client \
    -url=http://localhost:8080 \
    -workers=20 \
    -duration=30s \
    -intensity=7 \
    -output=results/demo/intelligent.csv

  curl -s http://localhost:8080/lb/stats > results/demo/intelligent_stats.json
  echo "cooling..."; sleep 20

  Point out: static weights — 40% latency, 40% CPU, 20% connections. Normalizes
  all three metrics and picks the best combined score. Avoids backend-1 without
  blindly dumping everything on backend-3. Sustains clean operation to 150 req/s
  in the full sweep — one step below the cluster ceiling.

────────────────────────────────
adaptive  (6/6 — no cooldown)
────────────────────────────────

  Restart LB in Terminal A with -algorithm=adaptive.

  go run ./cmd/client \
    -url=http://localhost:8080 \
    -workers=20 \
    -duration=30s \
    -intensity=7 \
    -output=results/demo/adaptive.csv

  curl -s http://localhost:8080/lb/stats > results/demo/adaptive_stats.json

  Point out: same as intelligent but weights recompute every 10s based on metric
  variance across backends. In this 30s run it gets ~3 recompute cycles. Under
  CPU-heavy load, CPU variance is high so it shifts weight toward CPU and behaves
  more like lowest_cpu dynamically.

================================================================================
3. SUMMARY TABLE
================================================================================

  python3 scripts/demo_summary.py results/demo

================================================================================
4. TEARDOWN
================================================================================

Ctrl+C in Terminal A to kill the LB, then:

  ./scripts/azure/teardown.sh

Double-check it's actually gone (costs money until it is):

  az group list \
    --query "[?contains(name,'inteliLB')].{Name:name,State:properties.provisioningState}" \
    -o table

================================================================================
QUESTIONS I MIGHT GET
================================================================================

Why 3 backends with different vCPUs?
  To simulate heterogeneous infra — cloud spot instances, preemptible nodes, mixed
  VM generations. If all backends were identical, routing strategy wouldn't matter.

Why does backend-1 get so many requests with some algorithms?
  Round-robin gives it exactly 33% by design. For metric-based algorithms,
  backend-1 (1 vCPU, taskset-pinned) sits at ~100% CPU under load so lowest_cpu
  correctly routes only ~18% there. An RTT tiebreaker on least_connections and
  lowest_cpu prevents tie-breaking bias toward backend-1 when primary metrics
  are equal.

Why is intelligent better than just lowest_cpu?
  lowest_cpu ignores network entirely. If the lowest-CPU backend is far away,
  you trade CPU headroom for worse latency. Intelligent blends both so you don't
  tank one metric to optimize the other. Also CPU% can't distinguish capacity —
  a 4-vCPU backend doing 4x the work reports similar CPU% to a 1-vCPU backend,
  so lowest_cpu routing between b2 and b3 is noisy.

What does adaptive actually add over intelligent?
  Intelligent has fixed weights (40/40/20). Adaptive recomputes weights every 10s
  based on which metric has the most variance across backends. Under CPU-heavy load
  it shifts toward lowest_cpu behaviour. Under uniform load it backs off and weights
  more evenly. The 10s interval gives ~3 recomputation cycles in a 30s demo run.
